# 修复推屏侧栏打开后汉堡按钮无法关闭

## 目标

修复推屏式侧栏导航的回归：抽屉打开后，汉堡按钮（位于被 inert 的主页面内）无法再次点击关闭抽屉，用户只能依赖左滑/Escape/菜单项关闭。

## 背景与根因

- `TabsPage.vue` 打开抽屉时把主页面容器设为 `inert`（`drawerInteractive`），阻止主内容交互。
- 汉堡按钮位于 `MNavbar`，属于子页面（RouterView）的一部分，在主页面容器内部。
- 因此抽屉打开时汉堡按钮所在子树不可点击，导致无法通过汉堡按钮关闭。
- 上轮设计已预留“主页面右侧透明交互区”方案：打开态主内容仍 inert，但用一个不遮挡侧栏、不影响视觉的透明点击区承接关闭点击。

## 需求

- 抽屉打开后，点击被推开的汉堡按钮区域（即主页面可见区域）应能关闭抽屉。
- 透明关闭交互区不遮挡侧栏（`0..50vw`），不改变推屏视觉，不引入覆盖式遮罩。
- 保留现有关闭路径：侧栏/主页面左滑、Escape、菜单选择、播放器/队列打开。
- 关闭后焦点恢复到汉堡按钮。
- 保持 MiniPlayer、弹层层级、平板固定侧栏不变。

## 验收标准

- [ ] 抽屉打开后，点击主页面右侧可见区域（含汉堡按钮原位置）能关闭抽屉。
- [ ] 侧栏区域（左侧 50%）点击仍只触发菜单选择/左滑，不被透明区拦截。
- [ ] 左滑关闭、Escape、菜单选择关闭行为不回归。
- [ ] 拖拽打开过程中不出现透明区异常拦截。
- [ ] 平板固定侧栏、MiniPlayer 与全局弹层不受影响。
- [ ] `npm run build`、`npm run lint`、`git diff --check` 通过。
- [ ] MuMu WebView 110 运行态验证：汉堡打开 → 点击透明区关闭 → 再左滑/菜单/Escape 正常。

## 范围外

- 不改变侧栏宽度、轨道几何、路由或业务逻辑。
- 不引入新的 UI 组件或依赖。
