# 刮削限流与退避——治 429

> 背景：刮削「全部开始」每首歌串行跑 5 文本源 + 6 封面源，无任何限流/退避，队列稍大即 burst 触发上游（Kw/Kg/Cloudflare）429。播放链路的 429 已治（缓存+停轮询），刮削链路仍裸奔。

## Goal
刮削全流程在 429 限流下优雅降级：不打爆上游、可观察、可重试，不丢队列。

## 范围
1. `ScrapeHttp` 全局限流：令牌桶/滑动窗口，默认 3~5 rps（可配置），跨文本/封面/歌词共享
2. 429 感知退避：命中 429 时指数退避（1s/2s/4s，尊重 Retry-After 头），重试 1~2 次后记为 `NETWORK` 失败而非无限重试
3. 匹配器层面：`TextMetaMatcher`/`CoverMatcher` 将 429 归为 `NETWORK`/`NO_MATCH` 可区分，触发 NegativeCache 短期跳过无效源
4. UI 提示：matching 态与 result 态对 429 有可读文案（「触发限流，稍后重试」），result 行可单独重试

## 非范围
- 播放/扫描链路（已治）
- 服务端限流阈值调整（用户自建站需自助）

## 验收标准
- [ ] 队列 20 首连续刮削不再稳定 429（或 429 后可见退避提示并最终有结果）
- [ ] 单首 429 不阻塞队列后续歌曲
- [ ] `testDebugUnitTest` 全绿，MuMu 实测匹配进度可读
