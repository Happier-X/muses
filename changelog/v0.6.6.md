# v0.6.6

## 修复

### 沉浸页开合改成「整页跟着卡片缩放」（#53 后续）

- 现象：打开 / 关闭沉浸页时，播放页的整块背景涌在卡片外面，没有被限制在正在形变的圆角矩形里
  （期望是椒盐音乐那种「圆角卡片连内容一起缩放」）
- 根因：`sharedBounds` 自带的形变在本版本（CMP 1.12）拿不到形变矩形——实测两种 `ResizeMode`
  都不会把矩形尺寸交给内容（`ResizeMode.scaleToBounds()` 无效果，`RemeasureToBounds` 只表现为
  「把按全屏布局的内容裁到矩形里」，于是转场中只看得到封面那一块）；另有三处叠加问题：
  1. `sharedBounds` 没传 `enter` / `exit` → 用默认 `fadeIn()` / `fadeOut()`，等于在整条转场上又叠了
     一层「整个沉浸页淡入淡出」，把形变观感盖住
  2. 封面用 `renderInOverlayDuringTransition = true` 独立画在 overlay 层，不随外壳裁剪 / 缩放
  3. 形变中外壳没有裁剪，内部 `fillMaxSize` 背景（深色底 / 流光图）仍按全屏绘制并溢出
- 修复：不再依赖 `sharedBounds` 的自动形变，改为宿主自己算
  - 迷你条用 `onGloballyPositioned` 上报自身矩形（`miniBarBounds`）作为形变起点，终点是全屏；
    **展开态与融合态的两个 `MiniPlayerBar` 实例都要上报**（`CompactPlayerDock` 新增 `onPlayerBounds`
    回调）——两边布局不同，只上报展开态的话，融合态下点开沉浸页会拿旧矩形当起点，
    而 app 一启动就是融合态时起点为空 → 直接没有任何形变（“融合状态没有开合动画”的原因）
  - 进度用 `Transition.animateFloat`（与 `animateTo` 同一条 380ms + FastOutSlowInEasing 时间线）
    从 `playerTransition` 取，所以照旧跟随系统「动画程序时长缩放」，下滑跟手的 `seekTo`
    也会逐帧体现在进度上
  - 新增 `PlayerShellBox`：布局固定用全屏约束（内容长什么样与全屏态完全一致），再按进度用
    `graphicsLayer` 的 `scaleX` / `scaleY` + `offset` 把整页缩放 / 平移到当前矩形，并带一个从
    12dp 收到 0 的圆角；外层 `clipToBounds()` 兜底
  - 封面不再走 `sharedElement`（`LocalPlayerArtworkKey` 不再 provide），跟着外壳一起缩放
- 实测（MuMu，把系统动画放慢 30× 逐帧采样）：转场中整个播放页（深色底 + 标题 + 封面 + 进度条 +
  控制栏）作为一张**圆角卡片整体缩小 / 放大**，卡片外是干净的主页面——即椒盐音乐那种效果

## 变更

### 曲库页顶部 tab 换成 miuix `TabRowWithContour`

- 原来用 `TabRow`：渲染成三个各自描边的独立胶囊；换成 `TabRowWithContour` 后是
  HyperOS 那种「整体一个大胶囊 + 选中项白色圆角块」的分段切换（`feature/library/.../LibraryScreen.kt`）
- 两者是 miuix 同一组件的两种官方形态，参数完全一致

### 底部安全区关掉系统「对比度 scrim」（不再出现白带）

- 现象：悬浮胶囊 / dock 下方的安全区（手势条 / 三键导航）是一条白块，与页面底色（`surface`，浅灰蓝）不一致
- 处理：
  - `MainActivity` 显式 `window.isNavigationBarContrastEnforced = false`（API 29+，minSdk 也是 29）
  - `themes.xml` 同步 `android:enforceNavigationBarContrast=false`（双保险）
  - 这样导航栏区域直接显示 app 内容（edge-to-edge 下就是页面底色），而不是被系统叠一层 scrim

### 沉浸页开合转场保持跟随系统动画设置（#53 结论）

- 现象：真机上点迷你条打开 / 收起沉浸式播放页没有任何展开形变（一帧到位），模拟器（MuMu）上正常
- 根因（已定位并复现）：系统「动画程序时长缩放」（`animator_duration_scale`，开发者选项；
  部分 ROM 的省电模式、无障碍「移除动画」也会把它置 0）为 0 时，Compose 的
  `Transition` / `sharedBounds` 会把整条转场**瞬时完成**
  - 排查中先排除：`v0.6.5` 的 tag 即转场提交、release APK 的 `classes.dex` 含
    `muses-player-shell`（不是发版漏带代码）、release 包重签名装到模拟器上转场正常（与 R8 无关）
  - 复现：`settings put global animator_duration_scale 0` 后点迷你条 → 首帧即全屏；
    设回 1x / 10x 立刻恢复正常转场
- 曾评估「绕开系统缩放」的方案（`withFrameNanos` 逐帧驱动 + `seekTo`，实测缩放置 0 时确实能播出完整形变），
  **经权衡不采用**：
  - 尊重显式设置——无障碍「移除动画」是晕动症 / 前庭敏感人群的刚需，而 `sharedBounds` 恰好是
    「全屏大幅缩放 + 位移」，属于最容易引发不适的运动类型
  - 避免节奏割裂——系统关动画时其余动画全是瞬时，唯独这里 380ms，容易被感知成「只有这里卡了一下」
  - 省电场景可能更差——关动画常伴随低端机 / 降频，`RemeasureToBounds` 逐帧重排的开销并不能被系统设置省掉
  - 维护成本——手写帧驱动绕开 Compose 的动画语义（驱动协程取消、中断续接、终态收敛都要自己管），
    后续升级 Compose 更易踩坑
- 结论：本转场继续走 `SeekableTransitionState.animateTo`，跟随系统动画设置。真机上「没有动画」属
  系统设置行为，不是 bug（CMP 1.12 已移除 `LocalMotionDurationScale`，app 侧也无法用
  CompositionLocal 局部覆盖该值）
- 顺带清理：`playerCollapseProgress` 自 v0.6.5 删掉「转场圆角 + 深色遮盖」后已无任何消费者，移除
- 转场时长抽为常量 `PlayerTransitionDurationMillis`（380ms），单源共用
