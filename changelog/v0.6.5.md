# v0.6.5

## 变更

### 转场卡顿优化

- 根因：`sharedBounds` 默认的 `RemeasureToBounds` 会**逐帧重排**整个沉浸页内容树，而沉浸页带全屏 `AsyncImage` + `blur(28dp)` 的流光背景，重排代价极高
- 措施：
  - 转场期间（`playerTransitionState.currentState != targetState`）把流光背景换成纯色底，转场结束再恢复（`PlayerScreen` 新增 `isTransitioning` 参数）
  - 删掉转场中每帧重建的 `clip(RoundedCornerShape)` 与全屏 `drawWithContent` 深色遮盖（曾为「让轮廓可见」而加，是额外开销）
  - 外壳 bounds 时长与 `playerTransitionState.animateTo` 用**同一条时间线**（同为 `tween(380ms, FastOutSlowInEasing)`）——若不一致，封面（`sharedElement` 受 `playerTransition` 驱动）会比外壳先跑完，看上去就是「封面一上来就全尺寸」
  - 时长定在 **380ms**（略长于 MeloX 的 360ms）：早先试过 260ms，配合 `FastOutSlowInEasing` 前段推进快，转场过半（200ms 左右）时封面/外壳已基本到位，观感上就是「一下就到」而非渐变
- 注：Compose 的 `ResizeMode.ScaleToBounds`（缩放绘制结果而非重排）在当前 CMP 版本不存在，否则用它能直接解决

### 封面共享元素转场（sharedElement）

- 参考实现 MeloX：外壳用 `sharedBounds`，封面**另行**用 `sharedElement`（`renderInOverlayDuringTransition = true` + `zIndexInOverlay = 100f`），封面会独立「飞」过去，比只做外壳形变更绲滑
- 本项目：新增 `PlayerTransitionLocals.kt`（`LocalPlayerSharedTransitionScope` / `LocalPlayerAnimatedVisibilityScope` / `LocalPlayerArtworkKey`），由 `MusesApp` 在两端各自的 `AnimatedVisibility` 分支里 provide；`MusesCover`（迷你条）与 `PlayerCoverHero`（沉浸页正封）读 Local 后挂**同 key** 的 `sharedElement`
- 用 CompositionLocal 而非逐层传参：封面深埋在 `MiniPlayerBar` / `PhoneImmersiveLayout` / `PlayerCoverHero` 好几层内部，传参会污染一串签名
- 封面 key 只在上述两处非 null，列表/首页封面保持 null，不会被误加转场

### 沉浸页下滑跟手收起（对齐 MeloX 的可中断转场）

- **正确做法**：`SeekableTransitionState` + `rememberTransition` + **`Transition.AnimatedVisibility(visible = { ... })`**
  - `SharedTransitionLayout` 内：`val transition = rememberTransition(remember { SeekableTransitionState(false) })`
  - 迷你条：`transition.AnimatedVisibility(visible = { !it }, enter/exit = None) { ...sharedBounds... }`
  - 沉浸页：`transition.AnimatedVisibility(visible = { it }, enter/exit = None) { ...sharedBounds... }`
- 手势：`PlayerScreen` 的 `onSeekCollapse(fraction)` → 宿主 `seekTo(fraction, targetState = false)`（跟手）；`onSettleCollapse(collapse)` → `animateTo(targetState = !collapse)`（**从当前 fraction 续接**，无跳变）
- 外部开关（点迷你条 / 点关闭 / 返回键）仍走 `LaunchedEffect(showPlayerOverlay) { animateTo(...) }`
- 踩坑：**不能**用 `AnimatedContent(targetState = SeekableTransitionState)`——内容与状态解耦后它不再做进出，沉浸页会彻底关不掉（返回键/下滑全失效，实测复现）；`Transition.AnimatedVisibility` 的 `visible` 是 `(T) -> Boolean` lambda，才能感知 seekTo 写入的中间进度
- MuMu 实测：慢速下滑中途，沉浸页沿 sharedBounds 形变到迷你条位置（能看到迷你条里的歌曲内容）；未达阈值松手后**从当前进度回弹**到全屏

### 沉浸式播放页改为「从迷你条展开 / 收起」转场（对齐 MeloX）

- 参考实现 MeloX-Android 用 Compose 官方的 `SharedTransitionLayout` + `sharedBounds`：迷你条与播放页共享同一个元素 key，转场时由 Compose 把起始矩形（迷你条）逐帧插值到目标矩形（全屏），而不是普通的整页滑动/淡入
- 本项目实现：
  - `MusesApp` 外层包 `SharedTransitionLayout`；
  - 迷你条与播放页各自包 `AnimatedVisibility`（`enter`/`exit` 均为 `None`，形变完全由 bounds 动画驱动），各挂同 key 的 `sharedBounds(..., resizeMode = RemeasureToBounds)`；
  - 时间线对齐 MeloX 的 `MeloXPlayerShellBoundsTransform`：**360ms + FastOutSlowInEasing**（不用默认 spring——弹簧会让父子元素各自提前/到达，出现「内容已就位但容器还在变形」的割裂感）；
  - `MusesApp` 标 `@OptIn(ExperimentalSharedTransitionApi::class)`
- MuMu 实测：连拍能抓到播放页从底部迷你条矩形向上长成全屏的中间帧

### 曲库页改为「歌曲 / 专辑 / 艺术家」Tab，歌单移除

- 窄屏底栏精简为三项后，专辑与艺术家在窄屏失去入口；现由曲库页内部 Tab 提供（新增 `LibraryScreen` 容器，顶部「曲库」标题 + `TabRow`）
- 三个子页以 `showTopBar = false` 嵌入：`MusesTopBar` 新增 `visible` 开关（函数入口直接 return）——若在每个调用处包 `if`，要动到带几十行 actions/bottomContent lambda 的调用点
- 歌单按产品侧要求从导航移除：`navItems` 去掉 `Playlists`、`NavDestination.Primary` 同步调整；路由与页面保留但不再暴露入口
- ⚠️ 取舍：`SongsPage` 顶栏里的「随机播放 + 歌曲总数 + 搜索」工具栏在嵌入模式下会一并隐藏（搜索仍可从底栏右侧圆钮进入）

### 迷你条封面尺寸收小

- 封面原先硬编码 44dp，在 56dp 高的迷你条里只剩 6dp 余量，观感偏满
- `MiniPlayerBar` 新增 `coverSize` 参数：常规态 44 → **40dp**，滚动融合态传 **38dp**
- 参考实现 Halcyon 正好是两档（常规 44dp / 紧凑 38dp，见其 `MiniPlayer.kt:460` 与 `:600`）；我们此前两处都用了 44dp，故融合态偏大

### 窄屏底栏精简为「探索 / 曲库 / 设置」

- 原 6 项（首页/曲库/专辑/艺术家/歌单/设置）在 360dp 宽上偏挤；收为 3 项 + 右侧搜索钮，每项空间充裕
- 「首页」更名为「探索」（`NavDestination.Home` 的 label 与页面大标题同步改），图标由 `Home` 换成 `Compass`（罗盘）
- ⚠️ 宽屏侧轨仍保留全部 6 项；**窄屏目前没有专辑/艺术家/歌单的入口**，如需保留应把它们做成曲库页的 Tab

### 底部 Dock 选中态：整块底色 → 图标 + 文字 + 滑动胶囊

- **根因**：底栏原本**只有图标**，选中态怎么做都「空」——整块 item 铺 12% 底色是笨重的大圆角矩形；44dp 正圆比图标大太多；撑满宽的 40dp 扁胶囊仍然是空
- 参考实现 Halcyon 的 `FloatingBottomBar` 之所以成立，是因为它的 item 里为**图标 + 文字两行**，气泡（撑满 tab 宽 × 56dp 高、`indicatorColor` 15%）恰好把两行包住
- 现对齐：item = 图标 24dp + 文字 11sp（间距 1dp），气泡撑满 item 宽 × 56dp 高、15% `primary`，随选中项 `spring(0.86, 520)` 位移；选中内容用 `primary`、未选中用 `onSurface`
- 顺带：底栏现在有可读的导航标签（原先 label 只进 contentDescription）
- 同时**收紧迷你条与底栏的间隙**：底栏原先额外 `.offset(y = 12.dp)` 下移（为「收紧底部留白」），使两件之间空出 20dp（迷你条 8dp 下边距 + 下移 12dp）；已去掉该下移，间距回归 8dp，避让值同步 148 → **136dp**

### 窄屏导航：侧滑抽屉 → 底部悬浮 Dock

- 窄屏不再用侧滑推屏抽屉，改回**底部悬浮导航胶囊**（悬浮迷你条 + 官方 `FloatingNavigationBar` 上下叠放），形态对齐 [Halcyon](https://github.com/Kifranei/Halcyon) 的悬浮 Dock（同为 miuix 体系：容器 `surfaceContainer`、选中 `primary`）
- 抽屉期间的三处额外成本随之消失：
  1. 内容整体右移（推屏）带来的布局与遮挡问题；
  2. 抽屉手势与内容区横向滚动（首页平台/榜单胶囊）抢事件——`startDragImmediately` 与自写 `pointerInput` 两条路都验证过不可行；
  3. 顶部状态栏与底部手势区的 inset 都要自己补（底部胶囊由 miuix 组件自带 inset）。
- 连带恢复：`PhoneBottomChromePadding` 96dp → 184dp（窄屏重新有底栏，列表末项避让同步加大）；移除为抽屉加的 6 个 inset 文件（`bottomSystemBarInset` / `topSystemBarInset` 的 expect/actual，已无消费者）
- 宽屏（≥768dp）保持官方 `NavigationRail` 侧轨不变

### 底部 Dock 滚动融合（借鉴 Halcyon）

- 列表**向下滚动**时，展开态的两行（独立迷你条 + 悬浮导航栏）**融合为一行**：`[当前 tab 图标] + [迷你播放器] + [搜索]`；**向上滚动**恢复两行
- 触发与阀值照搬 Halcyon 的 `BottomDockMode`：`NestedScrollConnection.onPreScroll` 里 `available.y < -12f → Compact`、`> +16f → Expanded`（不消费滚动，返回 `Offset.Zero`）；两阀值不等距是 Halcyon 的做法——向下敏感、向上需明确回滚，避免抖动
- 无歌曲时不进入融合态（没内容可融合）；点击左侧 tab 图标也可手动展开
- 融合态为给标题让出宽度：两侧图标 pill 用 48dp、中间迷你条**关闭队列按钮**（为此给 `MiniPlayerBar` 加了 `showQueueButton` 可选参数，默认 true，不影响既有调用）
- **细腻过渡**：同一个 `compactProgress` 弹簧（`spring(dampingRatio=0.88, stiffness=520)`，参数照搬 Halcyon）驱动两侧 pill 图标缩放 `1-0.14p`；布局切换用 `AnimatedContent`（淡入 180ms / 淡出 140ms）承接，两者叠加得到连续过渡（MuMu 实测能抓到图标正在缩放的中间帧）
- **三部分同材质**：融合胶囊的两侧图标 pill 与迷你条用**同一套材质链**（`surfaceContainer` 底 + 官方 `dropShadow` 阴影 radius 10dp/黑 20% + squircle 平滑圆角）；pill 为 **60dp 正方形**（圆角取半宽 = 正圆）——注意圆形必须用正方形，早期试过的「48×64 竖胶囊」会渲染成圆角矩形而不是圆；60dp 是「与迷你条 64dp 尽量齐高」与「给中间标题留宽」的折中
- **尺寸对齐 Halcyon**：迷你条内容高 **56dp**（封面 48→44dp、水平 padding 16→12dp、间距 12→10dp，对齐其「封面 44dp + padding 6×2」）；底栏容器强制 **64dp**（Halcyon 容器 64 / item 56；miuix 组件高度由内部常量决定、无高度参数，只能外层 `Modifier.height` 拉伸背景）；融合态两侧 pill 固定 **56dp 正方形正圆**，与迷你条严格齐平
- **底栏改为自研**（`MusesBottomDock`，替换 miuix `FloatingNavigationBar`）：官方组件的高度与图标尺寸由内部常量固定（IconSize 28 + IconPadding 10×2），**没有任何尺寸参数**，无法对齐 Halcyon 的「容器 64dp / item 56dp / 更大图标」；自研后：容器 64dp + 内边距 4dp + item 56dp（**等分全宽**）、图标 24dp、选中态 `primary` 12% 底 + `primary` 图标色，材质与迷你条同款（`surfaceContainer` + `dropShadow` + squircle）
- 连带简化：`chromeSideMargin` 不再需要按官方常量反推底栏宽度（自研后等分全宽），固定 18dp 与迷你条对齐
- 宽屏（≥768dp）不受影响（本就在用 Rail）

## 修复

### 进子页面时底栏停留在融合态

- 滚动融合态用的是 `rememberSaveable`，**切路由时没重置**：从列表页滚着进子页面（在线搜索/详情）时，底栏会带着上一页的融合态打开，显示成三部分胶囊而非完整导航
- 修正：`LaunchedEffect(currentKey) { bottomDockCompact = false }`（对齐 Halcyon 的 `LaunchedEffect(currentRoute, canCompact)`）

### 窄屏下底栏右侧被裁（修饰符顺序写反）

- `MusesBottomDock` 的左右边距原本写在它**自己的 modifier 链**上（`fillMaxWidth().padding(horizontal = 18.dp)`）：`padding` 在 `fillMaxWidth` **之后**，胶囊背景仍按全宽绘制 → 窄屏（MuMu 调 720×1280/360dp 实测）下右侧贴到屏幕边缘被裁，看着就像「tabbar 没展示全」
- 修正：边距改由**外层 Box 的 padding** 提供（与迷你条那边的写法保持一致：`padding(...)` 在 `fillMaxWidth()` 之前），两侧对称

### 底部 tabbar 被系统导航栏盖住

- 迷你条与底栏用的是**固定 12dp 底边距，没有任何系统栏 inset 避让**：`contentWindowInsets = WindowInsets(0,0,0,0)` 关掉了 Scaffold 的自动避让，而旧注释「系统手势区由该组件自吃 inset」说的是 miuix 官方 `FloatingNavigationBar` 的行为——底栏改成自研 `MusesBottomDock` 后，这个 inset 就没人吃了
- 修正：`bottomBar` 的 `AnimatedContent` 加 `Modifier.navigationBarsPadding()`（CMP 桌面端该值为 0，Android 上把整块底部 chrome 抬到系统栏之上）；并让 `bottomChromeHeight` 一并加上 `WindowInsets.navigationBars` 的 bottom，否则内容区挤压高度与抬高后的 chrome 不匹配，内容又会被盖住
- MuMu 三键导航模式实测：底部 chrome 整体上移约 24dp，落在导航栏之上

### 底部避让：滚到底留大片空白 / 展开后内容被遮

- 自研底栏 + 尺寸对齐 Halcyon 后，chrome **净高**变为「迷你条 72 + 底栏 64 + 下移 12 = 148dp」，而避让值仍是旧尺寸推导的 184dp → 滚到底部时内容与底栏之间多出大片空白（MuMu 实测约 250px）
- **最终方案**：内容区保持**全屏**（内容延伸到屏幕底、滚动时从悬浮 chrome 背后穿过）＋ 各页面**恒定**避让（窄屏 148dp / 宽屏 80dp，再叠加系统导航栏 inset）＋ 各页面普遍的 16dp 呼吸
  - 「恒定」是关键：避让值一旦随滚动融合变化，就会出现「避让变小后列表滚动位置不跟着变 → 展开回去时底部内容被多出的 chrome 盖住、且已到底再也滚不出来」的死角
  - 中途曾试过「内容区被 chrome 真实挤压」（壳层按 chrome 高度给内容区加 `padding(bottom)`）：滚动范围会自动收缩、永不被遮，但**内容被一刀切在 chrome 上方**、不再延伸到屏幕底部，滚到底观感生硬（悬浮 Dock 该有的「内容从背后穿过」没了），**已回退**
  - 参考实现 Halcyon 的对照（已拉源码核对）：内容区同样**全屏不挤压**（`Box { 内容; dock.align(BottomCenter) }`），各内容页写死 `contentPadding(bottom = navInset + 116/120/130/160dp)`，**内容页完全不感知 dock 融合态**；dock 则是 `navigationBarsPadding() + padding(bottom = 8.dp)`。本项目与其一致，区别是本项目用统一的 `LocalBottomChromePadding` 下发避让（Halcyon 是各页硬编码）
  - 那 8dp 保底抬升也一并采用：Halcyon 源码注释说明部分 OEM（ColorOS 某些模式）在显示手势条时会上报 nav inset = 0，光靠 inset 会让底栏贴住手势条

### 首页歌曲列表没有封面

- **榜单歌曲**：`SongListItem` 的 `SongItem` 数据类原本没有封面字段，首页榜单 20 首全是纯文字；现给 `SongItem` 加**可选** `coverUri`（传了才渲染封面位，不影响曲库/歌单等既有纯文字列表），首页榜单传入各平台远程封面（44dp、SM 圆角）
- **推荐歌曲**（猜你喜欢）：推荐行此前是序号 + 歌名 +（歌手 · 理由），无封面；现改为**封面 + 歌名 +（歌手 · 理由）+ 平台标签**（44dp、SM 圆角），并去掉序号（封面已承担行首的视觉锚点）
- 顺带补上数据层的封面缺口（此前三个来源返回 null，UI 只能落占位）：
  - **QQ（搜索 + 榜单）**：两个接口都不直接给封面 URL，改用专辑 `mid` 拼 `y.gtimg.cn` 标准格式（实测 10/10 成功）
  - **酷狗搜索**：实测 `AlbumImage` 恒为空串，真正有值的是 `Image`（且带 `{size}` 占位符，需替换）
  - **网易搜索**：该接口只给加密 picId（转 URL 需 AES），保持留空由 UI 落占位；网易**榜单**有明文 picUrl，不受影响
- 联网冒烟测试（`ChartProviderSmokeTest`）新增封面断言：QQ 榜单 / QQ 搜索 / 酷狗搜索均 10/10

### 在线音源：沉浸页歌词不显示

- **根因（MuMu 实机排查得出）**：封面/歌词此前只问洛雪脚本的 `pic` / `lyric` 动作。但脚本把这两个动作做成了 **`musicUrl` 的副产品**——直链请求时顺带把歌词/封面写进脚本内缓存，`lyric` / `pic` 只读缓存；而 Muses 的直链是「打开媒体时才换取」→ **切歌瞬间问 lyric 必然为空**，歌词自然不显示（导入的「星海音乐源」正是这种实现）
- 现改为「脚本优先 → Muses 匹配系统兜底 → 延迟重试选优」三段式：
  - **立即上屏**：脚本逐字歌词 > Muses 匹配结果（AMLL → 平台五源 → LRCLIB，与刮削同一条链）> 脚本行级歌词
  - **延迟重试**（1.5s / 3s）：等直链解析完成后回问脚本，命中**真实逐字**才替换
  - 不无脑替换的原因：实测脚本给的平台 LRC 会把末尾 credits 全标成 `[00:00.00]`（时间轴脏），覆盖后歌词会停在制作名单上
- 封面：脚本 `pic` → 搜索结果/榜单自带 → 六源匹配（iTunes→kw→tx→wy→kg→mg）→ 播放器实时 metadata；封面链慢，只在前面都没图时才跑
- 顺带修一个会让问题「永久化」的缺陷：元数据链（脚本歌词形态奇怪、解析异常）一旦抛错会**中断整条观察链**，之后切歌再也刷不出封面/歌词；播放页与迷你条均加异常兜底
- 验证：新增播放页 VM 层测试 5 项（在线·无脚本歌词→匹配上屏 / 在线·脚本逐字→采用 / 在线·脚本行级→不覆盖匹配结果 / 脚本迟到逐字→延迟替换 / 曲库曲目→曲库列）；MuMu 实机确认榜单在线曲目歌词正常（含中英翻译对照）且切歌正常更新

- 窄屏底栏 6 项（首页/曲库/专辑/艺术家/歌单/设置）；刮削与音源仍在 设置 → 工具
- 若后续要 Halcyon 那种「普通 / 模糊 / 液态玻璃」多模式与「底栏项可配置」，需要自研 Dock（Halcyon 的 `FloatingBottomBar` 是 651 行自研实现），当前用的是 miuix 官方组件
