# v0.6.7

## 变更

### 歌曲页「跳转当前曲」悬浮钮贴合底部 chrome（修「太高 / 还是离得挺远」）

- 报障（两轮）：歌曲页右下角回到当前歌曲的悬浮按钮位置**太高**，修完一轮后仍「**还是离得挺远**」
- 第一轮根因（`feature/library/.../SongsPage.kt` 的 `floatingActionButton` 槽）：FAB 抬升量硬编码
  `192dp（窄屏）/ 104dp（宽屏）`，按 v0.6.0「迷你条 80dp + 胶囊底栏 88dp」的旧 chrome 尺寸推的；
  两件套收窄到 56dp 后窄屏实际 chrome 比 192dp 矮约 40dp，FAB 悬在半空
- 第二轮根因：改成 `LocalBottomChromePadding`（恒定展开态 148dp）+ 16dp 后仍用的是**恒定值**；
  列表下滑时 dock 融合成一行（实际总高只剩 ~70dp），FAB 还按展开态 164dp 定位 → 空出约 90dp
- 第三轮（本条最终方案，真机像素级验证）：改为**实时可见顶**定位，迭代中排除了两个错误口径——
  - ❌ bottomBar 节点总高（`onGloballyPositioned` 报 size.height）：节点含透明 padding，
    实测比可见胶囊顶高 20dp，空隙 36dp；
  - ❌ 「距屏底高度」+ 扣 `WindowInsets.navigationBars`：miuix Scaffold 的 FAB slot 自带
    内缩（真机 FabBox 实测底/右各缩 12dp），而手势导航下 nav=0 扣不到 → 仍多空 12dp
- 处理（参考 Halcyon `HomeScreen.kt` 的 FAB 放置：`bottom = 176dp` ≈ 展开态 chrome 顶 + 少量呼吸，
  但它是硬编码，我们改成**实时可见顶**）：
  - `core/ui-shared/.../BottomChrome.kt` 新增 `LocalBottomChromeElevation: State<Dp>` =
    **迷你条可见顶的窗口坐标**（`miniBarBounds.top`，两形态都由壳层 `reportMiniBarBounds` 上报，
    且两态它都是最靠上的可见件）；State 形态下发，逐帧更新只重组读 `.value` 的 FAB
  - `feature/shell/.../MusesApp.kt`：`LaunchedEffect(miniBarBounds)` 逐帧换算，
    `CompositionLocalProvider` 包住整个 Scaffold 下发
  - `SongsPage.kt`：FAB 容器 `onGloballyPositioned` 实测自己 slot 的窗口坐标底，
    clearance = `slot底 − 迷你条顶 + 16dp` 呼吸——两者同为窗口坐标，与 slot 内缩来源无关；
    首帧未上报时退回恒定口径；多选条仍按恒定口径 + 64dp
  - 列表 `contentPadding` 仍用恒定 `LocalBottomChromePadding`——融合态跟随会让列表出现滚动死角
    （展开回去时底部内容被盖、已到底滚不出来），防遮挡口径不变
- 验证（MuMu 真机像素扫描）：融合态 FAB 底 1656px / 迷你条顶 1704px、展开态 FAB 底 1488px /
  迷你条顶 1536px，两态空隙均为 48px = **16dp**，从修前 90dp/36dp 收敛到位
- 编译：`:feature:library:compileKotlinJvm` / `:feature:shell:compileKotlinJvm` /
  `:app:assembleMusesDebug` 通过

### 底栏 TabBar 与旁边搜索钮的选中态统一

- 报障：窄屏底栏里 TabBar 项的选中状态与右侧独立搜索钮的选中状态**不是一套视觉**
- 差异根因（`core/ui-shared/.../MusesBottomDock.kt`）：
  - TabBar 选中气泡 = `primary` **15%** 底 + `primary` 图标/文字
  - 搜索钮选中叠底 = `onSurface` **8% × 0.72（≈5.8%）** + `primary` 图标
    —— 色相、透明度、动画到位值三处都不同
- 处理：`MusesDockActionPill` 的选中/按压叠底改为与 TabBar 气泡**同源**——
  `scheme.primary.copy(alpha = DockIndicatorAlpha * overlayAlpha)`（`DockIndicatorAlpha = 0.15f`），
  overlay 动画目标简化为 `pressed || selected → 1f`（原 selected 只到 0.72）
  - 图标仍保持选中 `primary` / 未选中 `onSurface`，与 TabBar 的 contentColor 口径一致
  - 按压缩放（1.06×）保留，属交互反馈不属选中态
- 编译：`:core:ui-shared` 的 `compileKotlinJvm` / `compileAndroidMain` / `compileCommonMainKotlinMetadata` 均通过

### 融合态底部胶囊两侧图标 pill 的按压反馈与分离态统一

- 报障：列表下滑进入「融合态」（两行合并为一行）后，点左侧 tab 图标 / 右侧搜索，
  按压时 pill 上会多出一个**方形灰色框**，与分离态（展开态）搜索钮的表现不一致
- 根因（`feature/shell/.../MusesApp.kt`）：融合胶囊两侧的 `DockIconPill` 是另起的一套实现，
  `.clickable(onClick = ...)` **没传 indication** → 落到主题默认 ripple，
  在方形 Box 边界内铺满 → 看着就是个灰色方框；而分离态 `MusesDockActionPill` 是
  `indication = null` + 「放大 1.06× + `primary` 15% 叠底」
- 处理：删掉 `DockIconPill`，融合态两侧直接复用 `MusesDockActionPill`
  （`core/ui-shared/.../MusesBottomDock.kt` 为其补 `size` / `iconSize` / `iconScale` 三个可选参数，
  默认值即分离态现状 56dp / 24dp / 1f；融合态传 `iconSize = 22.dp` 保持原观感）
  —— 两处同源后按压反馈不可能再漂移
- 编译：`:feature:shell:compileKotlinJvm` / `:core:ui-shared:compileAndroidMain` 通过

### 曲库页顶部 tab 收成紧凑居中（对齐 miuix 官方尺寸）

- 背景：v0.6.6 把曲库页 tab 从 `TabRow` 换成 `TabRowWithContour` 后，仍按整行 `fillMaxWidth`
  均分成三个大胶囊，观感与 HyperOS 的分段控件差别明显（miuix 源码里每个 tab 限宽 76~98dp，
  官方 demo 放页面级 tab 时用的是非 contour 的 `TabRow`，`TabRowWithContour` 多用于卡片内）
- 处理：`feature/library/src/commonMain/kotlin/com/muses/player/feature/library/LibraryScreen.kt`
  用一个限宽（252dp ≈ 3 × 76dp + 2 × 9dp 间距）的**外层 Box 收窄约束**再居中
  - 踩坑：`Modifier.width(...)` 不能直接传给 TabRow 的 `modifier` —— 组件内部是先
    `fillMaxWidth()` 再 `then(modifier)`，那样只会把内容往里挤、整条仍然撑满
- 实测（模拟器截图）：三个 tab 收成紧凑居中，选中项为白色圆角滑动块

### 沉浸页转场掉帧 + 「方卡片」

- 掉帧根因：转场进度（`shellProgress`）此前作为**参数**传进 `PlayerShellBox`，等于在组合期读取
  `State` → 进度每帧变化就**重组整棵沉浸页**（歌词 + 封面 + 模糊背景全在里面），380ms 内每帧一次
  - 修复：改成传 lambda（`progress: () -> Float`），只在 `offset {}` / `graphicsLayer {}` 的 lambda
    里读取 → 只让该绘制层失效重绘，不再触发组合
- 圆角：卡片圆角基数 12dp → **28dp**（= 迷你条胶囊半径 56dp / 2），到全屏收到 0；
  之前 12dp 在转场中期只剩几 dp，看着就是个方块（转场起止也不再是「直角弹出」）

### 沉浸页开合改成「等比浮入」（对齐椒盐音乐）

- 之前不自然的根因：卡片按「迷你条矩形 → 全屏矩形」**非等比**插值（scaleX / scaleY 分别算），
  而迷你条是宽扁矩形（约 972×168），于是转场中文字与封面被横向拉伸、竖向压缩
- 现在：整页**等比缩放**（scaleX == scaleY，0.92 → 1）+ **从屏幕下方浮入** + 圆角 **28dp → 0**
  - 以底部中心为原点，缩放时卡片底部不动、向上展开
  - 不再依赖迷你条矩形做形变起点（`miniBarBounds` 及其上报链路一并移除）
- 实测（模拟器把系统动画放慢 30× 抓帧）：卡片带明显大圆角从底部浮出，内容比例正常、不变形，
  卡片外是干净的主页面

### 沉浸页转场：改为「从迷你条位置生长」+ 除封面外内容渐隐（对齐椒盐音乐）

- 上一版的问题：起点在**屏幕外底部**（「等比浮入」），与迷你条之间没有任何几何联系，
  观感只是「一块卡片从下面冒出来」——用户报障「并没有从迷你播放条弹过渡到沉浸式播放页面」，
  且转场中期卡片是方形（圆角已修，但形态仍不对）
- 处理（`feature/shell/.../MusesApp.kt` + `feature/player/.../PlayerScreen.kt`）：
  1. 恢复**迷你条矩形上报**（`boundsInWindow`，融合态 `CompactPlayerDock` 与展开态各一实例都要报）；
     `PlayerShellBox` 起点由该矩形决定：
     - 缩放**只按宽度比** `miniBounds.width / fullWidth`（等比 → 内容永不变形），
       起点时卡片横向与迷你条等宽
     - 平移把卡片中心对齐到迷你条中心，`p = 1` 时位移归零即全屏
     - 用 `translationX/Y` 而非 `offset`：不进布局，避免每帧重新摆放内容
     - 拿不到矩形时（首帧）退化为原「底部浮入」兜底
  2. **除封面外的内容随进度渐隐**（`contentAlphaFor`：进度 < 0.45 完全不可见，
     之后按 `FastOutLinearInEasing` 浮现）：标题、歌词面板、进度条、控制按钮
     → 点开先看到「封面飞出来」，内容后半段才浮现；收起时相反
     - 封面本身仍走 share element（`PlayerArtworkSharedKey`），不受这个 alpha 影响
- 实测（模拟器系统动画放慢 10× 抓帧）：打开早期只有封面可见、卡片从迷你条位置生长；
  中期内容浮现；关闭时内容先隐、封面缩回迷你条位置——两向对称

### 修沉浸页「卡」（流光背景每帧全屏 blur 是主要开销）

- 定位过程（`dumpsys gfxinfo` 逐阶段拆解，非猜测）：
  - `Traversal`（组合/布局）= 0.04ms → 前几轮的「延迟读进度」修法有效，组合确实没在每帧重组
  - 瓶颈在渲染侧：`SyncQueued → SwapBuffers` 中位 15.75ms（UI 线程等 GPU）
  - 再按「沉浸页静止不动」做基线：中位 **25ms**、janky 帧 **90/92（97.8%）** —— 说明是**常态慢**，
    不是转场引入的
- 根因：`FlowLayers` 每帧对**全屏**做一次 `blur(64.dp)`。而它的输入是 25×25 的光栅网格色图，
  本就是低频色彩场，放大时 `FilterQuality.Medium` 的双线性插值已经是平滑渐变，
  这个全屏高斯模糊**纯属冗余**，每帧白烧一遍 GPU
- 处理（`feature/player/.../backdrop/FlowingLightBackdrop.kt`）：
  1. 去掉 `FlowLayers` 的全屏 `blur(64.dp)`
  2. 帧时钟降频到 **20fps**（`FlowFrameIntervalMillis = 50`）：流光只是「色彩缓慢呼吸」
     （游走周期 7/11/17/23s），20fps 与 60fps 肉眼无差别，但每帧要付网格色重算 +
     625 像素 Hermite 光栅化
  3. 每层各建自己的光栅位图（两层过渡时共用一张会互相覆写）
- 实测（同一台模拟器，沉浸页静止 6s）：

  | 指标 | 改前 | 改后 |
  |---|---|---|
  | 中位帧耗时 | 25ms | **7ms** |
  | 90 分位 | 31ms | 11ms |
  | janky 帧 | 90/92（97.8%） | **2/92（2.2%）** |

  转场（开关各 2 次往返）：janky 帧 **76/236（32.2%）→ 13/213（6.1%）**，中位 22ms → 18ms
- 视觉：改前/改后截图逐帧对比，背景流光观感一致，无马赛克/色块

### CarWith 车机适配：车机包沿用 QQ 音乐包名 + 会话歌词桥

- 车机包 `applicationId` 由 `com.miui.player` 改为 `com.tencent.qqmusic`（`app/build.gradle.kts` 的
  `miui` flavor）。CarWith 的媒体卡片/歌词卡片能力按**包名白名单**下发，非白名单包名拿不到
  歌词卡片适配——这是自用设备上的互操作取舍，仅本地自建自用，不对外分发冒充官方应用
- 新增 `core/media/.../playback/SessionLyricsBridge.kt`：向平台 MediaSession 注入
  `android.media.metadata.LYRICS` 全文字段（洛雪/椒盐的「车载歌词」走同一字段）
  - media3 的 `MediaMetadata` 是白名单字段对象，带不了自定义 key；本桥反射直取 media3 内置的
    legacy `MediaSessionCompat`（对外平台 token 正出自该会话），裸 Bundle 注入后回写
  - 幂等短路：回写前读系统会话现有 metadata，LYRICS 相同即返回；media3 每次重建 metadata
    都会丢 key，随 100ms 歌词轮询自动补回，最终一致（丢失窗口 ≤ 一个轮询周期）
  - fail-soft：任一步骤失败只打一条 w 日志并永久禁用本桥，不影响播放与通知
  - 除 LYRICS 外，bundle 其余内容（标题/艺术家/封面）以系统会话当前值为基底原样保留
- `PlaybackService`：解析歌词时缓存 LRC 全文（`lyricsRaw`），每轮 metadata 更新同步推送；
  切歌或关歌词模式时清空会话 LYRICS
- 兼容性：包名变更后与官方 QQ 音乐**签名不同、无法共存**（需先卸载官方版）；
  旧 `com.miui.player` 的本地数据（设置/曲库库表）不继承
- 编译：`:core:media:compileDebugKotlin` 通过

| 场景 | MuMu 实测 |

  其余长间隔来自两次操作之间的静止期（无内容变化不产帧），不属掉帧
